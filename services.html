技术文：为什么坚持零依赖

发版前最容易翻车的，其实就两类事。

一类是有人把 API key 顺手提交进了仓库。等 CI 跑完、镜像打好，密钥已经躺在 git 历史里，只能轮换、写事故报告，运气不好还得通知客户。

另一类是运营写的推文、投教文案里冒出「保本保收益」「老师带单」这类话术。金融行业的红线摆在那，一旦发出去就是事故，删稿都来不及。

这两类问题都不难查，难的是**每次都记得查**。靠人肉 review 迟早会漏，所以我把它们做成了流水线里的两个非零即红的步骤，加一个把两者串起来的组合命令。三个脚本都是纯 Python 标准库，没有第三方依赖。

一、密钥闸：toksentry

递归扫目录，把像密钥的东西揪出来。两套手段：

  • **正则规则**：AWS Key、GitHub Token、Stripe Key、Google API Key、PEM 私钥、JWT 这些有固定形态，直接匹配。
  • **香农熵**：拿不准的长随机串算一下信息熵，太"乱"就标出来让人确认。
    • python toksentry.py .                 # 扫整个仓库，命中即非零退出
python toksentry.py . --format json   # 给别的工具消费
python toksentry.py --self-test       # 不扫文件，只确认扫描器自己没坏

    不想扫测试样例、示例代码，写个 `.toksentryignore`（gitignore 语法）排除掉。

    二、内容闸：fin-compliance

    金融营销话术的红线是明文规定：不能承诺收益、不能暗示荐股、不能夸大、引流要留痕、AI 生成内容要显著标识。这个脚本做**文本模式标注**，规则放在 `rules.json` 里：

    | 类别 | 级别 | 典型触发 |

    |---|---|---|

    | 收益承诺 | high | 保本保收益、无风险、稳赚 |

    | 荐股暗示 | high / medium | 必涨、主力建仓、老师带单 |

    | 夸大宣传 | medium | 最牛、第一、100% |

    | 引流话术 | medium | 加微信、扫码进群、免费领 |

    | AI 生成未标识 | low | 全文没有 AI 标识 |

    python fin_compliance.py ./docs --fail-on high   # high 及以上拦下来
python fin_compliance.py ./docs --fail-on none   # 只出报告，不拦

    输出带行号和原文片段，能直接贴给合规同事复核。要按自己机构的口径增删规则，改 JSON 就行，不用动代码。

    这里得说清楚：它是**辅助标注工具**，不是法律意见，也不构成合规承诺。最终以人工复核和持牌法务意见为准。

    三、合成一条命令：release-gate

    两个工具各管一摊，发布前想一次查全，于是有了 `release-gate`：

    python release_gate.py /path/to/repo
python release_gate.py --code-dir ./src --content-dir ./docs --fail-on medium
python release_gate.py --self-test

    输出长这样：

    ① 密钥/令牌泄露扫描 (toksentry)
未发现密钥泄露。

② 金融内容合规标注扫描 (fin-compliance)
  samples/violation.md:4 | high   | 收益承诺 | 年化 15%，保本保收益...
  samples/violation.md:3 | high   | 荐股     | 这只票主力马上建仓，必涨！

结论:
  密钥泄露 : PASS (0 处)
  内容合规 : FAIL (7 处，阈值 high)
  总判定   : BLOCK 发布

    任何一闸不过，退出码就是 `1`。全过才 `0`。CI 不需要看懂报告内容，看退出码就够了。

    四、踩了一个自己挖的坑

    接进 CI 第一次跑，`toksentry` 就把自己的仓库扫红了。命中位置是 README 里的赞助链接，规则报的是 `Generic High-Entropy`，香农熵 4.363。

    第一版兜底规则写得很糙：

    {"name": "Generic High-Entropy", "pattern": r"[A-Za-z0-9+/]{40,}={0,2}"}

    只看长度，不看内容。于是 URL 路径、commit sha、一长串普通标识符全被当成疑似密钥。

    最省事的修法是在 `.toksentryignore` 里把 README 排除掉。但那是掩耳盗铃——README 里真写了密钥，就照样漏过去了。所以改的是规则：

  • 兜底规则加 `min_entropy: 4.5`，低于阈值的长串直接放过；
  • 匹配位置向左看 256 字符，取最后一个空白之后的片段，如果里面含 `://`，说明这串东西长在 URL 里，跳过。精确规则（AWS、GitHub、Stripe 那些）不受影响；
  • 顺手把 `re.findall` 换成 `re.finditer` 取 `group(0)`——PEM 规则里有个捕获组 `(RSA |EC |...)`，`findall` 会只返回组内容，命中记录里显示成 `"RSA "` 这种没用的东西。

    • 自检也改了：同一段随机串，一次独立出现、一次放在 URL 里，要求**只命中 1 条**。这样以后再动规则，误报抑制有没有退化一眼就能看出来。

    这类坑不写进文章里，看起来会更"完美"，但也就没什么参考价值了。

    五、为什么坚持零依赖

    不是洁癖，是三个很实际的约束：

  • **CI 镜像你动不了**。别人流水线里装什么包不由你决定，少一个依赖就少一个装不上、版本冲突的坑。复制一个 `.py` 就能跑。
  • **内网 / 信创环境不许联网装包**。金融、政企的打包机经常是离线的，甚至跑国产 OS。纯标准库刚好对口。
  • **代码和文案不能外传**。扫描在本地完成，不经过任何 SaaS。这一点在合规评审时比功能表管用。

    • 代价也清楚：规则得自己跟着新令牌格式、新监管口径维护，没有商业平台那种 dashboard 和集中报表。它解决的是「发布前拦一道」，不是「全公司密钥治理」。

    六、接进流水线

    三个仓库的 Actions 现在都是跑通的绿灯，可以直接看 badge 和日志。最小配置：

    name: Secret Scan
on: [push, pull_request]
jobs:
  toksentry:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: "3.11"
      - name: Self-test
        run: python toksentry.py --self-test
      - name: Scan repository for leaked secrets
        run: python toksentry.py . --format table

    建议卡三个位置：提交前（pre-commit，反馈最快）、合并前（PR 检查，防本地跳过）、出包前（发布流水线兜底）。密钥这一道建议零容忍；合规那一道可以分阶段——内部评审用 `high` 拦硬伤，对外发布前再上 `medium` 收紧话术。
